# Task 1 — F0 Detection, Prevention, and Operational Rollout Design

## Decision and evidence boundary

This is a **PROPOSED** prevention and operating design for the three accepted findings, not a deployed gate or a new remediation decision. [D0](phase-d-control-plan.md) selected F1 native image identity and Kubernetes process/filesystem constraints, F2 removal of unnecessary token projection and namespaced RBAC, and F3 Kubernetes NetworkPolicy for two east-west flows. Those choices remain the canonical remediation architecture. F1 and F2 were historically accepted as candidates in [D1](phase-d-d1-report.md) and [D2](phase-d-d2-report.md). D2 is the last **historically verified functional remediation baseline**. It says nothing about the current live runtime. Following the interrupted EXEC attempt, current cluster state and possible diagnostic residue are **UNKNOWN** ([interruption review](phase-d-d3r1b-exec-interruption-review.md)). No live cluster query, deploy, smoke test, repository script, or Make target was run for F0.

F3 is still blocked. During historical [D3](phase-d-d3-report.md), both candidate NetworkPolicies were admitted and selected their intended Pods, yet fresh API → unrelated target and unrelated source → backend TCP/8081 connections returned HTTP 200. Kindnet reported nftables synchronization errors; the precise failing operation and remediation remain unresolved in [D3R-1](phase-d-d3r1-diagnosis.md). The policy YAML remains a candidate. Its presence, successful parsing, API admission, and controller presence cannot stand in for dataplane enforcement. D4 integration and Phase E same-oracle proof remain dependent on a passing D3 gate.

The supporting records are the [source inventory](evidence/phase-f/f0-source-inventory.md), [claim trace](evidence/phase-f/f0-claim-traceability.md), [actual static output](evidence/phase-f/f0-static-checks.txt), and [scope record](evidence/phase-f/f0-scope-record.txt). This report describes future controls and gates; it does not claim they already exist. The future 3–5-page submission PDF should condense this design and use the completed D4/E evidence, rather than carry this report verbatim.

## Consolidated F1/F2/F3 control matrix

Each detection below has **exactly one primary category**. “Desired-state drift” compares declared files or permissions; “runtime observation” reads effective objects or process/controller state; “behavioral enforcement check” performs a bounded action that tests the restriction. A passed row in one category does not satisfy another row.

| Finding and accepted control | Proposed detection, primary category, and evidence | Owner and response |
| --- | --- | --- |
| **F1** — image-defined non-root API identity, `runAsNonRoot`, no privilege gain, `drop: [ALL]`, read-only root, writable ephemeral `/tmp` | **F1-D — DESIRED-STATE DRIFT:** review the pinned hardened Dockerfile and API template for the accepted fields, image lineage, `/tmp` mount, and absence of an extra writable `/app` mount. | Application owner maintains the image and template; security reviews changed policy assertions in CI. Reject a weakening PR or document a D0 revision. |
| F1 | **F1-R — RUNTIME OBSERVATION:** record admitted API Pod/image ID, actual PID 1 UID/GID, all capability masks, `NoNewPrivs`, and effective root, `/app`, and `/tmp` mounts. | Platform operator captures the canary after rollout and on drift alert; security compares it with the approved release. |
| F1 | **F1-B — BEHAVIORAL ENFORCEMENT CHECK:** normal repeated `/data` calls must write/read the cache; a harmless, cleaned-up `/app` create in the application context must fail; health and dependency traffic must pass. | Release verifier runs a bounded canary test. A failed write denial or required cache write blocks promotion. |
| **F2** — disable unnecessary ServiceAccount token projection for both workloads and remove the API fixture Role/RoleBinding | **F2-D — DESIRED-STATE DRIFT:** check both ServiceAccounts for `automountServiceAccountToken: false`, reject a Pod/template override or other credential mount, and compare desired Role/RoleBinding subjects and permissions with the zero-API budget. | Identity owner reviews the full desired permission inventory; CI rejects restoration of the fixture grant or any unexplained API grant. |

| F2 | **F2-B — BEHAVIORAL ENFORCEMENT CHECK:** in the actual API workload context, establish that the former named ConfigMap GET/PATCH path lacks a credential; if a justified identity exists, issue bounded real requests and require denial against a present harmless fixture. Preserve health, backend calls, and cache writes. | Release verifier owns the request oracle; `can-i` remains supporting authorization evidence only. |
| **F3** — API egress and backend ingress Kubernetes NetworkPolicy for the two selected TCP/8081 relationships | **F3-D — DESIRED-STATE DRIFT:** compare policy selectors, directions, peers, ports, DNS allowances, and the complete set of other selecting policies with the accepted graph. | Network owner reviews policy changes and additive allowances; CI flags broadening or missing policy declarations. |
| F3 | **F3-R — RUNTIME OBSERVATION:** inspect admitted policies, selected Pod labels, Service/EndpointSlice wiring, DNS endpoints, controller health and reconciliation errors, plus dataplane rule state where supported. | Platform/network operator triages mismatches and sync failures. This row never certifies actual denial. |
| F3 | **F3-B — BEHAVIORAL ENFORCEMENT CHECK:** use fresh Pod-to-Service connections with identified, healthy fixtures: API → backend and DNS UDP/TCP 53 pass; API → unrelated target and unrelated source → backend TCP/8081 fail; probes and functional client checks pass. | Release verifier and network owner jointly accept the result. This is the decisive F3 gate. |

This matrix does not expand F1 to the backend process or F3 to API ingress, backend egress, Internet access, or universal network isolation. Backend token removal is consistent hardening under its zero-API budget, not a second demonstrated F2 finding. Kubernetes policies combine allowed traffic across selecting policies, so F3-D must inspect the whole effective allowance set. [Kubernetes NetworkPolicy documentation](https://kubernetes.io/docs/concepts/services-networking/network-policies/) also states that a supporting network plugin is required and that API object creation alone has no effect without implementation. The F3-B probe therefore cannot be replaced by F3-D or F3-R.

The detector output should preserve the category in every alert and release record. A manifest mismatch is assigned to the application, identity, or network file owner for correction before merge. An admitted-object mismatch is assigned to the platform operator because a rollout, mutation, or stale Pod may have changed what actually runs. A behavioral failure is a release incident owned jointly by the service and security owners; the first action is to stop promotion and preserve its test context. This routing prevents a green source scan from closing a runtime or dataplane incident. A scheduled inventory can find drift after the merge gate, while the canary test gives the time-bound functional result needed to accept a release. Neither is continuous proof between test windows, so observed controller errors and unexpected grants should alert their owners as soon as they appear.

The evidence bundle for each future check should include the declared revision, effective object UID, image digest, test timestamp, expected result, observed result, and the identity or network path used. For F2, record only whether token paths exist and whether bounded requests succeed; never retain a token value. For F3, record both the healthy target control and the failed forbidden connection with source and destination identities. A timeout without target health or DNS resolution is inconclusive. If a workload changes labels or a DNS implementation changes endpoints, the network owner must reassess the selectors before trusting a previous pass.

## Proposed CI and admission architecture

The repository has a GitHub `origin`, but the tracked tree has no GitHub Actions workflow or other CI definition. **GitHub Actions is PROPOSED, not SELECTED or DEPLOYED.** It is a suitable single CI venue if the repository owner accepts GitHub as the release control plane. A pull request job would parse the intended manifest set offline; compare F1 fields and hardened image identity; reject F2 token overrides and any binding to the zero-API workloads; compare F3 policy objects and all declared selecting policies; and require review when image, RBAC, ServiceAccount, label, DNS, or NetworkPolicy files change. Tests must use deliberately insecure and acceptable fixtures, so a rule is shown to fail and pass for the intended reasons. The job would print a finding ID, resource path, expected property, and actual difference. The existing C0 Trivy scan corroborated some static conditions but did not establish process state, effective requests, or connectivity ([Phase C](phase-c-report.md)); it is supplementary coverage, not the gate’s oracle. No scanner or dependency was installed for F0.

The proposed merge gate is a required, non-skippable CI status plus review by the relevant owner. GitHub documents required status checks as a branch-protection mechanism; configuration and permissions must be verified by the repository owner before treating it as active ([GitHub branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). This design does not assume an existing protected branch, deployment workflow, or runner. Deployment remains an operator-controlled release step tied to the reviewed commit and recorded image digest until a delivery platform is explicitly chosen.

The CI job should parse every YAML document in the release set, reject duplicate object identities, and compare the rendered workload templates with the reviewed security contract. It should test negative fixtures such as `automountServiceAccountToken: true`, a RoleBinding to `demo-api`, a writable root, and an added unrestricted policy peer. A positive fixture must retain API → backend and both DNS transport allowances. These tests establish that the proposed source gate recognizes the intended drift; they do not show how an admission server or dataplane behaves. The job should publish the exact manifest revision it checked, and promotion should verify that the same revision and image identity are deployed. A pull request that changes an assertion needs security review so weakening the gate cannot be hidden inside a workload change.

For admission, **Kubernetes ValidatingAdmissionPolicy (VAP) is PROPOSED, not SELECTED or DEPLOYED** as one native mechanism, subject to a small proof in the target cluster. Kubernetes documents VAP as stable since v1.30 and supports binding actions `Warn`, `Audit`, and `Deny` ([VAP documentation](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/)). The policy scope would match the owned namespace and relevant workload, ServiceAccount, RBAC, and NetworkPolicy resource types. Candidate rules would reject a new API Pod or template without F1 constraints, a token automount override, creation of a grant to a zero-API ServiceAccount, and an unauthorized broadening of the two NetworkPolicies. Direct Pod creation and controller templates need separate match/field tests; a Deployment-only expression is insufficient. Cluster-scoped binding paths also need explicit coverage or a separately owned restriction. Keep VAP rules narrow to avoid blocking unrelated workloads.

VAP validates matched API requests; it does not inspect PID 1, prove actual token absence, guarantee that a required policy object exists, or attest that network packets are denied. Cross-resource relationships and the current union of selecting policies still require CI inventory review and runtime drift observation. The proposed admission pilot must demonstrate these gaps and the exact resource matches before enforcement. No Kyverno, Gatekeeper, new CNI, or second policy engine is selected. Any later need for one requires a concrete coverage gap and a separate architecture decision. Admission denial for unsafe creates and updates is preventive; runtime and behavioral checks remain separate release gates.

The VAP pilot should first submit representative safe and unsafe objects to an isolated namespace using the same resource kinds and operations that the eventual rollout will cover. Confirm that direct Pods, Deployment templates, ServiceAccounts, RoleBindings, ClusterRoleBindings where applicable, and NetworkPolicies are either matched or explicitly outside the rule scope. Test CREATE and UPDATE separately. A missed resource type is a coverage failure, even if another type is rejected correctly. Record admission warnings and audit events during the observation period, then compare them with the actual legacy inventory before enabling denial. This remains a proposed test plan; no admission object was created in F0.

## Acceptance, ownership, and rollback gates

Before implementation, the application owner approves legitimate startup, health, API → backend, and repeated cache behavior; the identity owner approves the zero-API permission inventory; the network owner approves the two denied flows, DNS and probe paths, source/target labels, and all other selecting policies. The security owner approves the CI assertions and admission test cases. The release operator records baseline error rate, latency, readiness/restarts, and policy rejection signals and agrees measurable canary thresholds with the service owner. F0 does not invent production service-level numbers. A changed D0 remediation objective or an evidence-based exception is a separate documented revision for review, never a silent F0 implementation change.

The proposed release sequence is: inventory legacy violations and dependencies; run CI and admission in report-only form against representative workloads; repair false positives; test the exact admission resource scope and failure handling; promote `Warn`/`Audit` to `Deny` for a small owned cohort; then expand by cohort only while functional and security gates pass. Audit findings need an owner and expiry. Exceptions must name the resource, property, business reason, compensating check, approver, and expiration; they cannot be permanent wildcard bypasses. [VAP actions](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/) permit a staged warning/audit and denial design, but a binding is not considered deployed until its actual cluster behavior is recorded.

Production change control should stage the hardened image and F2 identity cleanup before attempting F3. The exact RBAC cleanup needs an inventory of existing bindings and a targeted deletion or reconciliation plan: removing an object from Git alone leaves a live grant behind. Existing Pods may still carry projected tokens after a ServiceAccount change, so recreate the selected workloads and verify the new Pod UIDs and process-visible paths. Keep the baseline image and manifest identities available for comparison, but make each production rollback an explicit, scoped release action. Before F3 rollout, verify the policy implementation on the actual target cluster with the complete flow matrix; a passing test from a different cluster or an older CNI image does not transfer that result.

At each canary, first verify the release identity and effective Pod/permission inventory. Then run the shared functional oracle, F1-B and F2-B, and the complete F3-B fresh-connection matrix. A passing manifest diff, admission decision, or normal DNS request alone cannot pass F3. Separate the loopback `kubectl port-forward` diagnostic from ordinary policy-relevant ingress; the accepted F3 scope tests only the two selected east-west denials. Promotion requires healthy positive controls, both negative controls denied for the intended policy reason, no unexplained admission rejection, and no regression beyond the owner’s agreed service thresholds. Record UTC time, source and target Pod UIDs, image IDs, policy revision, controller/network version, and fixture health so a later pass cannot be mistaken for a current observation.

On a failed gate, stop expansion and preserve the diagnostic evidence. Revert only the pilot change to the last verified working release through the approved deployment process; for F3, remove or revert the new policy only within the affected cohort if it disrupts required traffic. That temporarily restores exposure, so the security and service owners must record the risk and a bounded compensating watch. A failed security denial cannot be waived as a successful rollout. Roll back admission `Deny` to `Audit` only when a verified false positive blocks legitimate work, retain the logged violation, and repair the rule before reenabling. Do not run a generic prune or restore the insecure baseline as a default rollback. Do not treat a rollback report from D3 as evidence of the current cluster.

## D3 dependency and exit condition

The next operational dependency is an authorized current-state and diagnostic-residue inventory after the interrupted EXEC attempt. It must establish ownership and the actual cluster state before any new mutation. The historical D3R evidence supports an unresolved kindnet nftables/netlink synchronization boundary, not selection of a new dataplane. A bounded diagnostic and any repair or environment change need their own reviewed decision. If the environment materially changes, repeat F1/F2 runtime and functional checks, reproduce the F3 pre-policy weakness, then run the full post-policy positive/negative matrix in that environment as [D3R-1](phase-d-d3r1-diagnosis.md) requires. Only a passing current-cluster F3-B result can unblock D3, D4 integration, and Phase E two-profile proof. Until then, F0 is a design artifact and **F3 remains NOT READY**.
